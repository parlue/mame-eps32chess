# 6502 execution and cached-data experiment

Baseline: combined Build 15, commit
`b8c1134bbde02a13c2f853cccb085fe23e4f71ef`, approximately 16% original speed.
The objective is execution speed, rather than another unused-code reduction.

## Measurement and experiment

`prepare_65xx_speed.py` composes an overlay on the owning 6502 memory-interface
source. An execution scope measures wall time inside `m6502_device::execute_run`,
counts calls and the decrement of the instruction-budget counter. The diagnostic
labels the latter `cycles`, but it includes cycles stolen when a timeslice is
aborted; the scheduler subtracts those separately. It is not a measurement of
actual total CPU cycles and is not used to derive the speed result. The OSD
reports these every five seconds,
along with the worker's stack high-water mark. This is wall time, including
preemption, rather than sampled CPU time. Timer/scheduler work outside
`execute_run` is excluded; memory and driver calls from inside it are included.
Two timer reads per invocation add measurement overhead to both compared paths.
The measured base object size excludes any additional derived-class storage.

The standard memory interface reads opcodes/operands through upstream MAME
access caches, but reads/writes ordinary data through virtual address-space
entry points. The experiment selects upstream cached byte access for data too.
It caches handler lookup, not RAM contents. Every access still invokes the
selected handler, including I/O and taps. Upstream change-notifier invalidation,
address masks and cache destruction are retained. Neither ROM maps, CPU
instructions, emulated clocks, interrupt scheduling, Lua/UCI timing nor watchdog
yield policy are changed.

The comparison is selectable before loading a machine using USB diagnostics.
Changes while the worker is busy are rejected. An atomic mode communicates the
selection to the MAME task. From Build 17, a selected interface subtype removes
the per-access mode check; the original `mi_default::read/write` bodies remain
untouched. Existing original-mode dispatch remains available for comparison.

The CPU, interface and cache addresses are logged to establish their memory
placement before allocating scarce internal RAM. Native CMake calls the same
generators; the combined common-SDK application is the device test target.

## Internal CPU object

Build 17 adds `prepare_mephisto_internal_cpu.py`. It changes only the Mephisto
driver's CPU construction site, using MAME's existing `device_add` creator API.
The same `m65c02_device`, dynamic type, zero-initialization, owner/tag, original
constructor and 9.8304 MHz / 2 clock are retained. Build 18 reserved a block of
exactly `sizeof(m65c02_device)` before Wi-Fi startup; from Build 19 reservation
is attempted only when explicitly selecting the optional internal-memory mode.
The normal owning unique_ptr destroys the object and releases this allocation;
later machines can allocate an internal block again. Allocation failure falls
back to ordinary allocation. The log identifies actual placement, so fallback
must not be described as successful relocation. No CPU header/layout change,
instruction change or direct bypass of mapped handlers is involved.

USB `mame-speed N` and test `--speed-mode N` select these modes:

| Mode | Ordinary data access | Mephisto CPU object |
|---|---|---|
| 0 (default from Build 19) | Original | Ordinary heap / PSRAM |
| 1 | MAME cached handler lookup | Ordinary heap / PSRAM |
| 2 | Original | Internal RAM when available |
| 3 | MAME cached handler lookup | Internal RAM when available |

`mame-cache 0|1` / `--cache-mode` remain aliases for modes 0/1. Selection is
diagnostic and resets to the default on restart. Build 18 reserved an internal
block at startup, including when later selecting mode 0. From Build 19 no
internal CPU block is reserved at startup; explicit selection of mode 2/3
attempts reservation before loading. This avoids occupying 12 KiB for a method
that has not demonstrated a speed improvement.
Build 16 measured at least 11,388 free worker-stack bytes across both ROMs.
Build 17 reduces its static stack from 32 to 28 KiB, reclaiming 4 KiB while
retaining over 7 KiB of that observed margin; the high-water mark remains
monitored. The opt-in HTTP diagnostic is also allowed during ROM execution,
with a device-test option to verify all six endpoints while MM V remains alive.

## Results

Build 16 succeeded (407.29 seconds), application 4,957,131 bytes and static RAM
158,724 bytes. Flash 12 and both full regressions passed, including actual
e7e5/d2d4, clean exits and UI return. Average MM IV/MM V speed was 14.97%/15.94%
with cache off and 14.27%/15.08% with cache on. That cache implementation was
slower, so it was not selected as a speed improvement. These were same-binary
comparisons with a per-access atomic mode check in both paths; Build 17 removes
that check. CPU execution wall share was approximately 85% in steady windows.
The CPU object was 12,344 bytes at a PSRAM address, as were both 44-byte access
caches. Stack reserve remained above 11 KiB. Evidence and exact images are in
`backups/takeover-20261110/combined-build16-6502-comparison`.

Build 17 linked successfully, but image inspection still found the old 32 KiB
worker stack: the final stack/HTTP edits had been made after that build had
already consumed the frontend sources. The checkpoint's 28 KiB assertion
rejected the image before flashing. Both frontend objects were explicitly
removed and rebuilt as Build 18; no intermediate Build 17 was flashed.

Build 18 succeeded (324.70 seconds), 4,955,751 application bytes and 154,604
static RAM bytes. Flash 13 verified all segments; the checkpoint validated the
actual linked 28 KiB stack. Same-binary full ROM regressions passed in modes
0 and 2: MM IV 16.49% versus 16.45%, MM V 17.33% versus 17.35%, both actual
e7e5/d2d4, clean exits and return to Virginia. MM IV's CPU was actually in
internal RAM, with no meaningful gain. MM V's CPU fell back to PSRAM after
intermediate configuration objects had released/reallocated the reservation;
its percentage is not an internal-versus-external comparison. The logs prove
placement rather than relying on the selected mode. Stack reserve stayed above
7 KiB in these paths.

The optional third run's six HTTP self-connect attempts to the board's own AP
address failed and the harness timed out, leaving MM V alive until the next
flash/reset. No panic occurred; both actual ROM moves had been observed, but
the third run is not a passed regression. This loopback diagnostic does not
establish whether a phone can access the AP. New physical phone access has not
been verified in this round. The full failed log is retained with the two
successful comparisons in `combined-build18-internal-cpu`.

## CPU compiler profile

Build 19 restricts `-O2` to `m6502_speed_s3.cpp` and upstream `m65c02.cpp`.
DWARF producer records confirm the actual options, including retained signed
char, exceptions, RTTI and the essential `-fno-merge-constants` identity fix.
This intermediate image built in 358.38 seconds (5,013,467 application bytes)
and was checkpointed without flashing or device testing.

Those records also exposed SDK defaults `-fno-jump-tables` and
`-fno-tree-switch-conversion`. The generated CPU interpreters dispatch through
large opcode/state switches. Build 20 explicitly allows `-fjump-tables` and
`-ftree-switch-conversion` for those same two sources, alongside `-O2`.
Other application/core sources retain their prior flags. The interpreters
already execute from flash in a normal worker task, requiring an enabled flash
cache; they are not cache-independent ISR code. No IRAM placement is implied.
Native CMake appends the equivalent per-source options after existing settings.

Build 20 succeeded in 336.11 seconds: 5,009,375 application bytes and 154,612
static internal RAM bytes. This trades 53,396 flash bytes for the CPU profile
relative to Build 15, while saving 4,080 static RAM bytes. The app remains
within its existing 8 MiB partition. Assets and ROM filesystem are unchanged.
Both CPU objects' DWARF producer records confirm O2, enabled jump tables and
switch conversion, retained RTTI/exceptions/signed char and disabled constant
merging. Both contain actual opcode-dispatch `.rodata` tables. Flash 14
verified every segment.

| ROM | Build 18 original path | Build 20 run 1 | Build 20 run 2 |
|---|---:|---:|---:|
| MM IV | 16.49% | 18.92% | 18.93% |
| MM V | 17.33% | 20.26% | 20.27% |

All entries are MAME's reported percentage of emulated time versus wall time.
The improvement relative to that measured original-path reference is about
15% for MM IV and 17% for MM V. Build 15 previously reported 16.12% for MM V;
the closer instrumented reference above is used instead of choosing that
lower baseline to inflate the gain. These are repeated short ROM/input tests,
including startup/ready and opening moves, not an isolated long search or
proof of sustained original speed. O2 and jump-table changes were measured
together; no independent jump-table-only improvement is claimed.

Device regressions `bauerino-device-19-cpu-dispatch` and
`bauerino-device-20-cpu-dispatch-repeat`, both `--no-captures` with default mode
0, passed actual MM IV e2e4/e7e5 and MM V d2d4, four result-0 exits with intact
heaps, return to Virginia, launcher/gestures, Bots/all 215 portraits, UCI Options
and board/notation. CPU addresses confirm PSRAM in both runs; no internal CPU
reservation is required for this result. The smallest observed worker-stack
reserve was 7,324 bytes. Internal heap while running was approximately 26 KiB.
No new physical finger/phone acceptance or screenshots were requested. The
failed optional AP self-connect diagnostic is not included as a passed check.

Exact binaries, source delta from Build 15, flags/table audit and all successful
regression evidence are retained at
`backups/takeover-20261110/combined-build20-cpu-dispatch`. The prior stable
Build 15 is unchanged as rollback. Intermediate experiment checkpoints retain
the unsuccessful alternatives. Native CMake wiring has not been independently
device-tested.

The next memory experiment should separate data-cache lookup from the cache
already used by instruction operands, to avoid alternating RAM/ROM accesses
evicting each other's lookup range. It remains future work; the slower shared
cache and unproven internal CPU placement are not enabled by default.
